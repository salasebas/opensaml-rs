# Migrating from `0.4` to `0.5`

This guide covers the changes consumers need to make when moving from the
latest `0.4.x` release of `saml-rs` or one of its compatibility packages to
`0.5.x`.

## Rust 1.88 is required

The minimum supported Rust version (MSRV) is now Rust 1.88 for `saml-rs`,
`opensaml`, `samlify`, `rustsaml`, and `samlet`. Update local toolchains and CI
before upgrading:

```sh
rustup toolchain install 1.88
rustup override set 1.88
```

The declared package MSRV applies even when `default-features = false`.

## The default crypto adapter uses Bergshamra 0.8

The default `crypto-bergshamra` feature now uses Bergshamra 0.8.0 and its
coordinated Kryptering 0.5 release. It remains a compatibility alias for the
RustCrypto provider plus Bergshamra's historical legacy-algorithm,
post-quantum, and PKCS#11 capabilities, so existing applications do not need
to change their feature selection.

Bergshamra 0.8 makes provider initialization, key import, and unsupported
operations fallible. `saml-rs` preserves its existing public error taxonomy:

- provider and key-import failures return `SamlError::Crypto`;
- a missing operation key returns `SamlError::MissingKey`;
- an invalid detached signature still returns `Ok(false)`.

Applications that also use Bergshamra directly must handle the new
`Result<Option<SoftwareKey>>` shape returned by key-import methods such as
`Key::to_signing_key()`. Concrete RustCrypto RSA accessors were removed; use
provider-neutral key metadata and exports such as `Key::algorithm_name()` and
`Key::to_spki_der()` when inspecting public keys.

New applications can select a minimal RustCrypto, AWS-LC, or FIPS provider with
`default-features = false` and exactly one of `crypto-rustcrypto`,
`crypto-aws-lc`, or `crypto-fips`. Bergshamra supports the last two on Linux
x86_64/aarch64; the `saml-rs` provider matrix currently validates Linux x86_64
and does not exercise Linux aarch64. Provider features are mutually exclusive,
so workspace `--all-features` builds are intentionally unsupported.

`saml-rs` initializes and attests the selected provider before its first crypto
operation. Call `initialize_crypto_provider` during application startup to
fail early and inspect `CryptoProviderInfo`. In `crypto-fips` builds a successful
result reports `CryptoFipsStatus::Active`; this is active provider attestation,
not certification of the consuming binary or deployment. Initialization,
attestation, capability, and key-import failures remain fail-closed through
`SamlError::Crypto`.

The FIPS provider rejects algorithms outside its approved set. In particular,
the currently exposed `RSA_OAEP_MGF1P` XML-Enc key transport uses SHA-1 and is
not available in FIPS mode. AWS-LC has narrower RSA-OAEP, AES-KW, finite-field
DH, legacy, and post-quantum coverage than RustCrypto. The provider CI matrix
therefore runs common SHA-256 XML-DSig, detached-signature, metadata-trust, and
XSW regressions, plus positive AWS-LC and fail-closed FIPS XML-Enc coverage.

## XML signature trust behavior is unchanged

Inbound SAML XML signatures continue to use metadata-pinned keys only, strict
signed-reference placement checks, a 160-bit minimum HMAC output length, and
local digest/reference coverage checks. Inline `<KeyInfo>` material is not a
trust anchor. The adapter still skips public-CA certificate chain and time
validation because SAML metadata certificates are treated as pinned key
material; signature, digest, duplicate-ID, reference, and wrapping defenses
remain enabled.

The software RSA key-transport compatibility opt-in is unchanged. It remains
disabled by default because the RustCrypto RSA backend is affected by
RUSTSEC-2023-0071.
